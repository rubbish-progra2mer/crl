# v009 主研究者重新扩张决定

## h-011 死亡后的有效边界

h-011 的因子实验未得到“协议阶段语义”特异效应：审计记录、通用记录、普通事件和无关动作事件同样触发危险提交，状态极性的作用又在模型间分裂。因此，继续改写“完成、覆盖、核验、提交”类提示只会留在已经被 P076、ToolGate、arXiv:2608.02464 以及本 Run 多个负结果压缩的同一盆地。

## 新科研坐标

下一版本转向**并行工具返回的数据关联不变量**，贡献形态只预注册为协议鲁棒性评价/稳定现象：

- 一个模型回合发出两个或多个调用，调用具有独立标识、工具名和参数；
- 固定调用与结果的真实对应、多重集合及最终问题，只置换结果消息的到达/呈现顺序；
- 正交操纵调用标识是否正确、标识与顺序是否冲突、载荷是否自带实体线索、工具名是否相同；
- 测量正确标识下的置换不变性，以及标识与位置冲突时模型实际采用哪条绑定通道。

这与 h-011 的完成线索不同：对象从“是否认为义务已完成”改为“把哪一个返回值归属于哪一个调用”；因变量从读取/提交首动作改为实体—值对应正确率与成对置换一致性；评价载体从串行工作流记录改为并行调用协议。

## 最近先行边界

- AgentCheck（arXiv:2607.11098）的 12 类响应故障覆盖超时、接口错误、权限、模式漂移、陈旧、矛盾、错误答案、静默空值及安全攻击，不包含结果重排、调用标识冲突或并行调用错配。
- BFCL 已评价并行和多重并行函数**调用生成**；其并行 AST 匹配明确不要求模型输出与答案保持相对顺序。它没有把执行结果返回后的调用—结果绑定作为独立因果轴。
- AsyncFC（arXiv:2605.15077）已经维护 future—execution association，并把“标识到已解析值”的绑定消息插入上下文；它也把并行执行顺序语义和状态竞争作为系统问题处理。因此“用标识配对”“恢复确定顺序”“未来对象”均不得作为新方法。本候选只能询问模型/协议栈在等价置换和冲突通道下是否保持语义绑定。
- Anthropic 官方协议要求每个结果用 `tool_use_id` 对应调用，执行顺序由调用方决定；这使“正确标识、任意完成顺序”成为真实协议条件，而不是人为坏格式。
- OpenAgentLoops 已同时按标识与原请求顺序配对，并指出部分 Qwen/GLM 工具解析器会产生调用标识碰撞。因此“规范化回原顺序”已有工程实现；若异常只在缺失/碰撞标识时出现，研究增量不足。
- 本地 Ollama 并行工具示例只返回 `tool_name` 并按调用顺序追加结果，同名、不同参数的并行调用没有独立 `tool_call_id`。因此本地原生协议不能单独支持跨供应商的标识因果结论；实验必须区分原生顺序通道与显式序列化标识通道，并如实限定外推。

## 进入条件与立即杀死条件

进入 v010 的理由是研究问题、协议载体、核心自变量和测量对象均发生实质变化。只做一次最小高信息量检查，不预设方法贡献。

立即淘汰条件：

1. 正确且唯一的调用标识下，三个本地模型在多个领域都对结果置换完全不变；
2. 所有效应只出现在缺失、重复或错误标识等无效协议输入；
3. 仅载荷匿名时失败，而载荷自带实体字段即可完全解释；
4. 只在一个模型或单一提示模板复现；
5. 最近先行已经完成相同的标识×顺序×载荷自识别因子评价；
6. 本地协议无法把标识与顺序通道分开，导致结果只能说明文本位置敏感而非工具协议绑定。

若出现跨模型、跨领域、正确标识条件下的稳定置换非不变性，或在标识—顺序冲突中稳定错误优先采用位置，才允许继续扩成 benchmark/phenomenon；任何修复都必须超出已有的唯一标识检查和原序重排基线。
