## Changed computation

CRAFT 把“模型针对每个新问题从零生成一段完整代码”改成“离线构建经回放验证的任务专用函数库，在线按问题需求检索少量函数并复用执行”。具体计算链为：

1. **多样化采样**：从训练集或指令数据的 `(problem, answer)` 对出发；先随机取样，再以 SimCSE 表示计算候选问题到已选集合的最大相似度，每轮加入最不相似的 100 个问题，以覆盖不同问题模式（物理页 3）。
2. **具体程序生成与执行过滤**：GPT-4 为采样问题生成 Python 具体解；仅保留能执行且得到已知正确答案的解（物理页 4）。
3. **函数抽象**：GPT-4 将具体实体名泛化、把内部硬编码文本提升为参数，并生成函数名和 docstring，使一次性程序成为可复用函数（物理页 4；提示词与代码例见 16–25）。
4. **原题回放验证**：把抽象函数交给 GPT-4，由其为原始问题填入参数并执行；不能重现原题答案的函数被丢弃（物理页 4）。
5. **去重**：先按函数名与参数个数分组，再让 GPT-4 在每组中选择适用面最广的函数（物理页 4；提示词见 25–26）。
6. **三视图检索**：在线时，待评估 LLM 先根据目标问题预测“需要的函数名”和 docstring。系统分别以目标问题对原创建问题、预测函数名对库存函数名、预测 docstring 对库存 docstring 做 SimCSE 检索，三路 `k` 分别为 10、5、10；按三张列表中的出现频次聚合，取最多三个高频函数，并过滤仅出现一次的函数。若全部仅出现一次，则退回直接代码生成（物理页 4、15、26–29）。
7. **复用执行**：把检索到的函数实现加入提示，LLM 生成调用这些函数的代码；函数与调用代码实例化执行后得到最终答案（物理页 4）。

可迁移的最小机制不是“多模态工具调用”，而是：**从有答案的文本任务样例中提炼小型可执行函数，以原题回放保证最低正确性，再以问题/函数名/docstring 的多视图语义信号检索复用**。

## 输入、输出、信息与时点边界

| 时点 | 输入 | 可见信息 | 输出 |
|---|---|---|---|
| 离线采样/生成 | 训练或指令数据中的问题与答案 | 已知答案；问题语义；执行环境 | 经执行过滤的具体 Python 解 |
| 离线抽象/验证 | 具体解、原问题、抽象函数、原题答案 | GPT-4 可见抽象任务；验证阶段可利用原题与正确答案判断执行结果 | 通过原题回放的泛化函数、函数名、docstring |
| 离线去重 | 同名且同参数数目的函数组 | 组内实现与说明 | GPT-4 选出的单个较通用函数 |
| 在线检索 | 当前问题；由决策 LLM 预测的函数名与 docstring；工具库存的原创建问题/名称/说明 | 不应见测试答案；可见库存元数据 | 至多三个多视图高频工具，或空集合 |
| 在线求解 | 当前问题、检索函数代码、基础解释器/领域库 | 检索函数及其实现 | LLM 生成的调用代码及执行答案 |

文本方向可直接吸收表格处理和数学推理中的函数抽象、回放验证、元数据检索与执行复用。VQA 的图片输入、ImagePatch 方法、视觉模型结果及由此产生的增益均越出本轮边界。

## 实验与强基线

- 主实验使用 GPT-3.5-Turbo-0613 作为 CRAFT 与各基线的在线骨干，覆盖 GQA、OK-VQA、A-OKVQA、TabMWP 和 MATH algebra（物理页 5–6）。强基线包括：无工具 CoT；Vanilla/Program-of-Thoughts 或 ViperGPT；外部 Python 库；LLM-created-tool 方法 LATM 与 CREATOR；同一 CRAFT 工具库上的单视图 SimCSE 与 BM25 检索（物理页 5–6）。
- **边界内的 TabMWP**：CRAFT 88.4% accuracy，高于 CoT 75.2、Vanilla 80.6、外部库 83.1、LATM 9.3、CREATOR 81.0、单视图 SimCSE 83.8；但低于同工具库的 BM25 89.2。因此论文不能据该数据声称三视图检索在所有文本任务上最优（物理页 6）。
- **边界内的 MATH algebra**：CRAFT 68.1%，高于 CoT 50.9、Vanilla 58.2、外部库 41.1、LATM 30.3、CREATOR 65.0、SimCSE 36.7 和 BM25 35.9（物理页 6）。但只评估 algebra 子集的 881 题；作者明确说未评估其余 MATH 子集是预算所限（物理页 5）。
- 论文报告 VQA 上相对强增益，并做抽象、多视图字段消融、GPT-4 骨干和工具库规模分析（物理页 6–8）；这些结果依赖视觉工具载体，本轮不用于准入。值得注意的是，抽象与检索字段消融也只在 VQA 上报告，不能直接证明文本方向每个组件的因果贡献（物理页 7）。
- 工具规模分析只比较 0、261、337、525 个 VQA 工具；观察到单调上升，但不能证明“理论上无限扩展”仍保持收益（物理页 8）。工具库报告 525/181/282 个 VQA/表格/数学工具及平均圈复杂度 2.64/2.07/1.34；低圈复杂度只说明控制流简单，不等价于语义正确或鲁棒（物理页 8–9）。
- CREATOR 在论文复现中被移除其格式检查与纠错，只比较 one-pass accuracy；这一改动使其不再是完整原方法的等成本比较，解释主结果时必须保留该条件（物理页 6）。

## 预算、模型与 oracle 边界

- 工具创建、抽象、验证和去重依赖 GPT-4；主实验在线骨干是 GPT-3.5-Turbo-0613。GPT-4 骨干分析因预算仅在 VQA 上与 ViperGPT 比较（物理页 4、6、8）。
- 作者估计三个工具库的构建总成本约 2,500 美元，但没有给出按数据集、阶段、token 或重试拆分，也没有给出在线检索/代码执行的完整延迟和成本对照（物理页 3）。
- VQA 工具源自 2,000 个指令问题（首轮 1,000，后续 10 轮各 100）；TabMWP 与 MATH 各从训练集采 500 个问题（首轮 200，后续 3 轮各 100）（物理页 15）。最终工具数分别为 525、181、282（物理页 8–9）。
- **oracle 仅限离线**：具体解过滤和抽象函数验证都使用原创建问题的已知答案；测试时的检索与求解不应访问测试答案。该验证证明“能回放创建样例”，不证明函数在分布外参数、异常输入或组合调用下正确（物理页 4）。
- 去重裁决由 GPT-4 基于函数实现作主观选择；它不是可执行等价性证明。在线三视图检索固定 `k=(10,5,10)` 并最多返回 3 个函数，论文未给出文本任务上的 `k` 敏感性、tie-breaking 细节或检索 token 上限（物理页 4、15）。
- TabMWP/MATH 的工具构建使用下游训练集而非测试集；这属于有监督的任务内适配，不应表述成完全无数据适配的开放域能力（物理页 3、15）。

## Failure 与限制

1. **适用性受代码可表达性限制**：作者明确承认目前只适合可通过写代码求解的任务，并把伪代码扩展留作未来工作（物理页 15）。
2. **强依赖骨干的工具使用能力**：开源骨干在作者 pilot 中接近随机；工具库不能自动补足不会正确调用工具的模型（物理页 6、15）。
3. **“正确工具”主张偏强**：验证只回放创建它的原题，未系统测试参数域、边界值、异常、函数组合或分布外问题。附录中的 `find_inverse_value_linear` 用 `while current_output != target` 持续乘倍数；若目标不可达、浮点不精确或倍数不合适，可不终止，恰好说明低复杂度和原题通过不足以保证一般正确性（物理页 24–25）。
4. **抽象可能引入语义漂移**：GPT-4 同时改变量、提升参数、命名和写 docstring；回放原题只能检出部分漂移，不能验证更宽泛 docstring 所声称的全部输入空间（物理页 4、16–25）。
5. **去重覆盖有限**：按“同函数名+同参数个数”分组会漏掉异名同义工具，也可能把同名但语义不同的函数放在一起；最终仍由 GPT-4 选一个，缺少等价性或回归测试（物理页 4）。
6. **检索聚合脆弱**：多数频次启发式可能在三路信号分歧时返回空集；固定 top-k、最多三工具和仅出现一次即过滤会牺牲稀有但精确的工具。文本数据没有针对这些规则的完整消融（物理页 4、7）。
7. **基线与成本未完全对齐**：CREATOR 被改成 one-pass；CRAFT 的昂贵离线 GPT-4 工具构建没有与各基线做统一成本核算，且 TabMWP 上 BM25 略优（物理页 3、6）。
8. **范围外证据占主分析比重**：抽象、字段消融、骨干升级和规模曲线集中在 VQA；在本轮文本/代码函数边界内，只能把 TabMWP 与 MATH 主表视为直接任务证据（物理页 6–8）。

## 准入与第三读建议

- **准入：是，但必须窄化准入。** 准入对象是“样例驱动的可执行函数提炼 + 原题回放过滤 + 问题/名称/docstring 多视图检索 + 在线复用执行”这一文本/代码工具机制，以及 TabMWP/MATH 的边界内实验。不得把 ImagePatch、视觉编码、视觉问答增益或“跨模态泛化”吸收进当前方向。
- **证据等级判断**：机制描述充分且有边界内主表支持；但组件级因果证据主要来自范围外 VQA，且正确性、成本和基线公平性仍有限。因此它适合作为 mechanism/operator 来源，不足以单独支撑“普适可靠工具库”或“三视图检索总是优于简单检索”的强主张。
- **建议第三读：是。** 建议第三读专门核对三件事：文本任务上 abstraction/retrieval 各组件的真实贡献；工具在非原题输入上的语义回归与终止性；在统一 token/API/离线构建成本下对 BM25、CREATOR 与直接代码生成的公平比较。
