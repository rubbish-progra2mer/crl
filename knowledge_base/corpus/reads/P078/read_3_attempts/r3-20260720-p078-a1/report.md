## 核心结论

CRAFT 确实改变了推理时可执行计算：它不是只检索文字示例，而是离线创建并验证 Python 函数，在推理时检索函数源码、置入提示，再由模型生成调用代码并执行。但论文只用“抽象后工具回放其来源原题”验证单个工具，不能证明该函数对未见实例或未见分布的泛化；尤其附录中的工具明显存在定义域过窄与不终止风险。三视图检索的总体消融支持“额外的名称/文档字符串视图有用”，却没有给出与 BM25 或 CREATOR 在 LLM 调用、检索候选数、提示长度、修复机会及总成本上的等预算对照。因此，本篇可作为“训练样例诱导可执行工具库 + 检索条件化执行”机制及同基准性能的证据，但不可作为工具泛化、安全终止或成本公平性的强证据。

## Changed computation 核对

### 实际改变了什么

1. 离线计算链发生实质改变：从源数据抽样问题，由 GPT-4 生成具体 Python 解；仅保留可执行且答对来源问题的代码；再由 GPT-4 做变量泛化、参数化、命名和 docstring；用同一来源问题调用抽象工具复验；最后按函数名与参数个数分组，由 GPT-4 选择较通用者去重（物理页 3–4）。这会生成持久的、任务定制的可执行函数库，而非只改变自然语言提示。
2. 推理计算链也改变：被评估 LLM 先从目标问题生成预测函数名与 docstring；系统分别以问题、函数名、docstring 做 SimCSE 检索，按三表出现频次投票并过滤仅出现一次的工具；将入选函数源码加入提示，模型生成调用代码，随后与工具一起执行得到预测。若没有工具通过投票，则退回直接代码生成（物理页 4–5、15、26–29）。
3. 因果归属仍不完全清楚。最终系统同时改变了离线数据加工、提示内容、一次额外的“描述需求”LLM 推断、检索器和可执行上下文。论文的 `w/o Abstraction` 与三种视图消融说明这些组件对端到端指标有贡献，但没有隔离“复制/改写正确程序思路”“调用原函数”“更长提示”各自贡献（物理页 7–8）。

### 文本/代码函数的适用范围

- 作者明确承认当前方法限于能通过编写代码解决的任务；计划中的伪代码扩展尚未实现。工具效果还高度依赖骨干模型的 tool-use 能力，试验中的部分开源模型接近随机（物理页 15）。因此，“广泛适用”目前只在 VQA、表格处理与 MATH-algebra 三类任务中获得展示，不能外推到非代码化任务。
- VQA 函数的真实计算依赖 `ImagePatch.find/simple_query` 等视觉模块；表格和数学函数依赖 pandas、SymPy 或 Python 解释器。论文并未把这些底层模型/库的错误与 CRAFT 自身错误分开（物理页 2、5–6、16–24）。
- “低圈复杂度”只表明控制流分支少，不等于语义正确、定义域完整或执行安全。作者以平均圈复杂度 2.64/2.07/1.34 支撑“可靠”表述，但没有异常、边界值、安全沙箱或资源上界测试（物理页 8–9）。

## 原题回放与泛化证据

### 原题回放不足以证明函数泛化

- Validation 明确使用“原先用于生成该工具的同一个问题”：让 GPT-4 给抽象函数传入适当参数，能重新得到原答案就保留（物理页 3–4）。这是来源实例回放，最多证明抽象没有破坏该实例，不是独立样本验证。
- 具体代码解在抽象前也以来源问题的已知答案筛选（物理页 3–4）。因此，生成、筛选、抽象后验证三步都围绕同一题，存在强烈的实例适配选择效应。
- `w/o Abstraction` 在三组 VQA 上低于完整 CRAFT，提供了“抽象步骤对总体端到端性能有增益”的证据；但它没有报告逐工具在未见问题上的成功率、与来源题的相似度分层、跨数据集迁移，或抽象函数对反例/边界值的测试（物理页 7）。
- TabMWP 与 MATH-algebra 的工具直接来自各自训练 split；测试可支持“同基准留出样本”层面的系统泛化，但没有说明近重复题、模板重合或每个被检索工具是否解决了不同于其来源题的计算结构。VQA 工具来自 LLaVA 与基于 COCO-2017 构造的指令问题；OK-VQA/A-OKVQA 也基于 COCO 图像语境的潜在重合或近重合没有在文中审计（物理页 5、15）。这里不能据文中材料断言发生泄漏，但也不能排除。

### 可复核的失效例

- 附录给出的 `find_inverse_value_linear` 使用 `while current_output != target_inverse_output` 并持续乘以 `common_multiplier`。若目标不可达、倍率为 1/0/负数、方向错误，或浮点比较永不精确相等，循环没有终止保证；函数也没有迭代上限、可达性判定或异常返回（物理页 24–25）。这直接反驳“来源原题通过即可视为可靠”的强解释。
- VQA 示例在找不到 reference object 时退回 `simple_query(query)`，找到多个 reference 时只取第一个；这改变了多实例场景语义，且对检测器漏检、多个对象、遮挡等情况没有验证（物理页 16–17）。
- 表格总价示例在项目不存在时静默跳过，并取同名项目第一行；对重复键、缺失条目、字符串货币、单位不一致没有约束（物理页 20–22）。这些函数对来源题有效不等价于其 docstring 所暗示的通用契约。

## 三视图检索：与 BM25/CREATOR 的公平性

### 相对 BM25/SimCSE

- 有利点：论文称替代检索法使用同一份 CRAFT 创建的工具库，因而工具质量大体受控；完整 CRAFT 在多数数据集优于单一 SimCSE/BM25，但 TabMWP 的 BM25 为 89.2，反而高于 CRAFT 的 88.4（物理页 6–7）。三视图分别移除问题、名称或 docstring 都会使 VQA 指标下降，支持三视图内部效用（物理页 7–8）。
- 关键不公平/缺报：CRAFT 先调用被评估 LLM，为目标问题生成函数名与 docstring，相当于获得一次生成式 query expansion；BM25/SimCSE 被描述为问题/API 名称间的简单相似匹配，文中没有说明它们是否获得同一生成式扩展、相同的三视图文本、相同最终工具数、相同候选预算或相同提示 token 数（物理页 4、6、15、26–29）。
- CRAFT 的三个候选表使用 `k=10/5/10` 后投票，最终最多三工具且可能为空；文中只给了这些 CRAFT 参数，没有给 BM25/SimCSE 的对应 k、调参集、排序聚合或失败回退细节（物理页 4、15）。因此只能说“作者实现下优于所列替代检索”，不能说在等检索/LLM预算下证明三视图优越。

### 相对 CREATOR

- CREATOR 每个测试问题在推理期创建一个专用工具，CRAFT 则离线用 GPT-4 建立 181–525 个工具并在推理期检索复用；两者改变计算的位置、可用监督量和摊销方式不同（物理页 6、8）。
- 作者为所谓公平比较，移除了 CREATOR 原方法中的格式检查与纠错，只报告 one-pass accuracy（物理页 6）。这并非保持原方法完整能力；同时 CRAFT 自身保留了离线“生成→执行筛选→抽象→原题复验→去重”的多阶段质量控制。若目标是比较系统最高能力，这一处理偏向 CRAFT；若目标是严格 one-pass 推理，则仍需把 CRAFT 的离线多次 GPT-4 调用与摊销成本纳入。
- 论文没有报告每个方法的总调用数、失败重试、生成/检索 token、工具构建摊销点、解释器运行次数或墙钟时间，故无法做成本匹配。仅凭准确率不能建立与 CREATOR 的资源公平性。

## 预算、oracle 与安全/终止

- 已披露预算：三类工具库合计估算约 2,500 美元（物理页 3）；MATH 只测 881 道 algebra，因为全子集超出预算（物理页 5）；GPT-4 只在 VQA 上与 ViperGPT 比较，也因预算限制（物理页 8）。工具规模为 VQA 525、Tabular 181、Math 282（物理页 8）。
- 未披露：离线各阶段 GPT-4 调用/重试次数与 token，候选失败率，推理时“描述需求”调用成本，最终代码生成成本，视觉子模型调用数，解释器时间/内存、延迟及摊销假设。因而论文的成本信息不足以支持部署或与在线工具创建方法的总成本比较。
- Oracle/监督来源：具体解以已知训练/指令答案执行筛选；抽象工具又以相同原题答案复验。这是离线标签 oracle，合法用于训练数据加工，但必须与“无需监督”或“零样本泛化”区分。VQA 部分声称不依赖强监督，却仍使用生成问答、过滤器以及具体解正确性判断；其答案来源和自动评估误差没有全面量化（物理页 3–4、15–16）。
- 非终止与运行风险：论文只说把函数和生成代码交给解释器执行，未报告超时、循环上限、资源配额、沙箱、文件/网络权限、异常处理或恶意代码防护（物理页 4–5）。附录已有显式无界 `while` 例证（物理页 24–25）。所以“bug-free”“可靠”应理解为在来源题运行成功，而非全输入终止或安全。

## 争议结论

1. **“工具正确且可靠”——不接受强表述。** 原题回放和低圈复杂度不足以建立未见输入正确性、安全性与终止性；附录反例显示无界循环和窄前置条件。
2. **“抽象促进泛化”——有限接受。** 端到端 VQA 消融支持抽象有用，但没有逐工具独立测试或跨分布验证，不能把增益等同于函数契约泛化。
3. **“三视图检索优于 BM25”——仅在作者实现和多数所测数据集内成立。** TabMWP 上 BM25 更高，且生成式 query expansion、候选 k 与 token/调用预算不匹配。
4. **“优于 CREATOR”——准确率事实可记录，方法公平性不足。** CREATOR 的检查/纠错被移除，而 CRAFT 保留昂贵的离线多阶段筛选；缺少总成本与摊销对照。
5. **“plug-and-play、适用于未见域/模态”——证据边界较窄。** 当前实现只覆盖可代码化任务，并严重依赖闭源强模型及外部视觉/数值工具；作者自己报告开源骨干接近随机。

## 准入判断

**有条件准入。**

- 可准入的主张：离线从训练/指令问题创建可执行函数库、推理时以问题/名称/docstring 三视图检索并执行，能在所报告三类基准与作者实现设置下提升部分端到端指标；该工作也提供了“检索到的可执行过程会改变推理计算”的明确机制实例。
- 不准入的主张：原题回放证明工具对未见问题泛化；低圈复杂度证明可靠；三视图在等预算下普遍优于 BM25；CRAFT 在资源公平条件下优于完整 CREATOR；工具执行具有终止、安全或已量化成本保证。
- 后续若将本篇用于方法论论证，必须附带限定：训练/指令答案 oracle、同题验证、生成式检索扩展、离线成本未充分摊销、无终止/沙箱报告，以及只在特定可代码化任务中验证。
