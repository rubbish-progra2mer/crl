## 一、结论先行

CRL 的方向有意义，但当前产品还不能被视为“只要持续运行，就会越来越接近一个值得投入的实现”的科研机器。它目前更准确的性质是：**科研协议、隔离工作区、检索工具、实验记录器和固定评审器的集合**。工程真实性约束较强，科研搜索的反馈控制、持续执行和真实有效性证据较弱。

Run13 是严重失败案例。失败的核心不是本地模型或实验后端连续无响应，而是：

1. 主研究者把搜索优化成了“快速提出一个候选—寻找已有工作—立即关闭—推进版本”；
2. 负面记忆持续增长，正向候选没有形成相同强度的晋升与资源分配通道；
3. 机器允许主研究者绕过结构化候选、先行审计和实验工具，直接用 Markdown 完成大量科研裁决；
4. `ACTIVE` 执行会话在推进到空的 v173 后断尾，既无 Delivery，也无 No-Delivery、暂停、终止或合法外部边界交接；
5. CRL 尚无真实、时间截断、专家盲评的研究发现评测，不能证明它比裸大模型更容易找到值得投入的实现。

因此，**不建议现在直接恢复 Run13，也不建议原样启动 Run14**。应先修复 P0 级目标与控制回路，再用一个短而真实的对照 Run 验证修复是否改变“只读论文并快速否定”的行为。

## 七、当前 CRL 机器审计

### 已确认的工程优点

1. 产品根、机器根、知识库根和 Run 隔离规则清楚；
2. 知识库科学内容只读、Run 间隔离、重解析点和路径越界防护较强；
3. Formal 记录包含命令、规格、实现和输入输出哈希、预算、环境、标准输出/错误、指标和超时状态；
4. 固定三评审器的 packet、键和最终绑定逻辑较完整；
5. 当前完整测试为 500 通过、15 跳过、0 失败；另显式启用真实知识库/真实 PDF 标记后，相关 9 项测试全部通过；
6. 当前版本已经补入版本转向 continuation、schema 2 不可变决策事件和更严格 Recall 排除等 Run13 之后的改进。

### 仍存在的关键缺陷

#### P0：没有真实的研究发现有效性证据

`evaluation/research_discovery` 只有人工合成夹具，README 明确声明“不代表真实科研能力”。固定 Reviewer 的校准只能证明评审器能区分人工构造的强弱材料，不能证明 CRL 能比裸模型更好地发现课题。

#### P0：CRL 不是持续运行服务

`crl.py capabilities` 显示所有 Recall、Diagnosis、Tool、Recorded、Review 能力均为 optional，`required=[]`，`workflow_gate=false`。机器本身没有后台研究循环、自动续接器或会话结束保证。真正工作的是一次 Codex 任务中的主研究者；任务断开后，CRL 不会自行继续。“不限制时间和额度”在当前产品层面并不等于持续执行。

#### P0：目标口径在执行中被错误收窄

当前 `CRL.md` 明确允许方法、稳定经验现象、基准/评价、系统能力和理论/分析贡献，并说 Seed 不必是全新计算原语。Run13 后期却反复以“只是已有组件作用到新对象”“不是新计算”为理由关闭候选，实际执行标准比权威协议更窄。这会系统性漏掉最适合本地资源的评价、基准和现象型实现。

#### P0：只有淘汰棘轮，没有对称的晋升棘轮

负面记忆非常强，任何新候选很快会与 172 版历史或经典方法发生相似；但机器没有要求维护少量仍存候选、下一项会使其升降级的关键证据、最低实现投入和预期扩大价值。结果是“越运行，越容易找到否定理由”，而不是“越运行，越集中资源验证最有希望者”。

#### P1：当前检查器噪声反而遮蔽真实断尾

用当前 `inspect_run.py` 检查 Run13 v173：

- 用时 136.71 秒；
- 报告 485 个错误；
- 485 个全部是 `workbench_v*` 中第三方 Markdown 使用 CRLF；
- 非 workbench 错误为 0；
- v173 的 11 个主要研究文档和 4 个研究目录全部不存在，却没有被标成错误。

也就是说，检查器把外部仓库换行符当成 485 个 Run 完整性错误，却没有突出真正重要的“ACTIVE 当前版本为空”。

#### P1：历史机器身份不可复现

工作区没有 Git 仓库；Run Charter、Status 和 Ledger 不记录机器版本、协议哈希或主研究者指令哈希。Formal execution 只绑定当次运行器及少数模块哈希。由于当前 `CRL.md`、`manage_run.py`、Diagnosis 和假设管理代码均在 Run13 后修改，无法从资源包精确重建每个历史版本当时使用的整机代码与提示。

#### P1：结构化工具是可选旁路

Run13 后半段证明，主研究者可以停止使用 `portfolio.json`、Prior Audit 和 Formal，仍然高速写 Markdown 并推进版本。当前协议强调低摩擦有合理性，但对“关闭候选”“推进科学版本”“形成先行碰撞”这类不可逆科研裁决缺乏最低可审计约束。

#### P1：资源卫生较差

Run 内虚拟环境、完整仓库和大型外部数据使资源包膨胀到 2.17 GB；Recall 和 `inspect_run` 又会受这些内容影响。共享环境已经在 `CRL_ENVIRONMENT.md` 中固定，Run 内重复创建大虚拟环境没有科研收益。

## 九、Run13 中最值得保留的一条线索

当前只能称为“待重新评估线索”，不能称为已验证 Seed：**v172 的论文复现留出干预响应评价**。

它有三个优点：

1. Run13 对 PaperBench 23 份真实评分表、12,038 个评分节点做了可复查静态审计，发现实现和已发表消融检查很密集，但显式评分器生成的留出干预响应项几乎没有；
2. 目标载体真实存在：Replica、PaperBench、ReplicationBench 都是公开的论文复现任务；
3. 它天然能形成一个可运行评价协议和本地小规模试验，符合用户需要的“实现先行”，不需要本地训练大模型。

Run13 关闭它的理由也真实：差分故障注入、蜕变测试和主动测试都已有先行机制。在线核验确认 [Replica](https://arxiv.org/abs/2608.13331)、[差分故障注入](https://arxiv.org/abs/2608.14527)、[PaperBench](https://proceedings.mlr.press/v267/starace25a.html) 和 [ReplicationBench](https://arxiv.org/abs/2510.24591) 均真实存在，v172 不是凭空编造文献。

但“组件已有”只足以否定把它包装成全新测试原理，**不足以自动否定基准/评价贡献**。当前权威 CRL 协议本来就允许评价型 Seed。v172 真正缺失的是：在自然存在而非人为植入的错误复现上，留出响应测试能否发现现有评分表漏掉的机制错误。这个高信息量实验没有运行。

因此，v172 是 Run13 中最值得在新控制回路下重新审视的线索，但其潜力仍为中等且高度不确定；现在不能直接交付给用户投入扩大实验。

## 十、面向唯一终极目标的修复优先级

唯一目标应写成：**交付一个“投资就绪的实现核心”——它有真实可运行 artifact、至少一个本地高信息量结果、可信的最近先行边界、明确的扩大实验计划和失败边界，值得用户继续投入；不要求本机完成整篇论文。**

### P0：下一次正式 Run 前必须处理

1. **修正主研究者口径**：关闭候选前必须分别检查方法、现象、评价/基准、系统和分析贡献；经典机制碰撞不能自动杀死新评价贡献。
2. **建立正向候选漏斗**：任何时刻保留 1—3 个“最值得下一单位资源”的存活实现线索，记录晋升所需证据，而不是只积累失败记忆。
3. **限制实验前连续关闭**：连续多个候选在实验前关闭时，不再继续同样的“读新论文—自然修补—先行碰撞”循环；必须切换到公开数据上的现象验证，或形成诚实 No-Delivery。
