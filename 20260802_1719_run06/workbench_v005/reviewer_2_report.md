## 核心漏洞

### 阻塞项：相关性判定与一致性检查之间仍可能存在组合盲区

当前顺序是：

```text
relevant =
  targets(K_outer)
  OR targets(K_payload)
  OR record_targets

若 relevant，才检查：
  K_outer != K_payload
  或 record.cell != K_payload.cell
```

这意味着，一致性异常本身可以先使三个完整相关条件全部为假，随后该观察便永远不会进入一致性检查。81 项说明覆盖了九类单字段重标和“请求范围外、记录范围内”，但没有说明覆盖这两类异常的组合。

固定材料没有明确说明 `record_targets` 中“页面来源与快照”究竟取自外层键、载荷键，还是两者的保守并集。若按最直接的文字含义取外层页面来源，则存在以下最小错误认证构造。

设主张为：

```text
来源 S，范围 {B}，快照 σ：
是否存在满足 P 的 B 单元记录
```

输入只有两张完整保留的已认证观察：

```text
o0:
  K_outer = K_payload = (S, B, σ, 起始游标)
  records = []
  可信终止
o1:
  K_outer   = (T, A, σ, 起始游标)   # T != S
  K_payload = (S, A, σ, 起始游标)   # A 不在 {B}
  records   = [r]
  cell(r)   = B
  P(r)      = true
```

`o1` 是请求 `S/A` 的真实且正确关联响应，只是响应中出现了一个真实归属 B 的记录；外层来源被错标为 T。它不要求伪造请求—响应关联，也没有删除输入页。这正是方法声称要失败关闭的“外层重标 + 记录—请求单元不一致”。

按照上述文字定义：

- `targets(K_outer,C)=false`，因为来源是 T；
- `targets(K_payload,C)=false`，因为请求单元 A 在范围外；
- 如果 `record_targets` 使用外层页面来源，则也为 `false`；
- 因此 `o1` 在检查 `K_outer != K_payload` 和 `cell(r) != A` 之前被排除；
- `o0` 单独闭合 B，求值器可错误认证存在假；
- 第二实现路径若重算同一相关谓词，也会排除 `o1`；
- `audit_observation_digests` 不会包含 `o1`，所以该承诺不能挽救此次漏选。

全称方向有完全对偶的构造：`o0` 支持全称真，`o1` 含一个 B 单元反例记录，仍可能被排除。

如果实际实现已经明确使用 `K_payload` 的来源和快照计算 `record_targets`，这个具体输入应当返回 `UNKNOWN`；但固定材料没有把这个关键选择形式化，也没有说明 81 项中存在上述组合项。因此我不能依据本次同字节材料确认漏洞已关闭。

### 请求键只有字节规范化，缺少语义唯一性前提

当前规范 JSON 检查保证字段精确和重序列化字节唯一，但不保证请求键值对连接器语义是单射的。例如大小写别名、统一码等价形式、端点别名、默认值显式与省略、版本别名，都可能形成两个字节不同但连接器语义相同的自洽请求键。

“载荷覆盖所有语义参数”不等于“语义相同的请求必然映射到同一个 `RequestKey`”。如果这种单射性不成立，一张语义上属于当前请求的冲突页可以因操作、版本或单元别名而被当成真正异源页。该问题至少需要新增明确前提，真实连接器阶段则需要验证。
