## 为什么仍不交付

第一，核心计算与基于假设的部分可观测运行时验证高度重合。按观察一致世界汇总真值、确定时给结论、不确定时拒绝，是已有方法谱系的中心语义；多探针关系与超性质监控重叠，黑盒事件规格监控也有 SpecMon 强基线。当前真值表枚举与不可识别见证是该有限片段的直接构造，没有形成独立于这些工作的新理论对象或算法优势。

第二，授权层是必要可靠性修复，但主要由 HMAC、规范序列化、完整绑定、有效期和重放保护组成；in-toto/SLSA 已经占据来源工件与消费验证空间。把已知部分观察判定和已知来源绑定放进同一工件，当前证据只证明组合可工作，尚不足以构成 CCF-B 方法增量。

第三，扩大实验没有显示可识别合同上的相对方法优势。在诚实观察器且合同可识别的 544 例中，候选和公平直接观察规格基线都是零错误接纳、零错误拒绝。候选在 680 个诚实观察器案例中的价值，是拒绝不可识别合同并消除直接基线的 12 个错误接纳，但同时产生 72 个保守错误拒绝；这验证了安全策略，不证明新的检测能力。

第四，观察器真实性仍是端到端接入的关键缺口。观察器掩盖错误状态时有 58 个错误接纳。候选已诚实限定签发者与观察器可信，因此这不反驳条件定理，却表明最实际的系统保证仍由未验证的观察边界决定。

第五，证据独立性仍不足。SQLite 与 Git 使用不同状态引擎和不同状态/观察存储，但合同目录、40 个故障算子及适配器均由同一主研究者编写；没有独立作者成本、遗漏率或维护实验。继续由同一作者扩充变异，难以改变新颖性与同源性结论。

## 正交路线复核

我复核了四条非机械转向，而不是把当前候选失败等同于整个问题失败：

1. **投影实现一致性/观察器真实性证明**：可用远程证明、多方见证或交叉状态源约束 58 个反例，但主要落入远程证明、可验证日志和传感器信任，需新的系统假设与真实基础设施；当前没有独立于成熟来源/证明工作的最小方法核。
2. **把时间窗、重试和最终一致性纳入投影语义**：这能修复 Git 固定两轮执行器的局限，但直接进入实时时序逻辑和部分可观测运行时验证的强碰撞区；没有新的归纳结构或复杂度结果前，只是扩大已知框架。
3. **独立作者的合同合成与维护研究**：它是必要评价，可能证明工程价值，但单独不能补出方法新颖性；当前也没有诚实可得的独立人工作者，不能用代理指标替代。
4. **升级到公钥来源链/透明日志**：能增强部署可信度，但属于用成熟 in-toto/SLSA 机制替换 HMAC 原型，不改变方法核。

这些路线都值得未来作为新的、明确版本重新形式化，但在当前 Run 边界与已完成证据下，没有一条已经形成可交付的 CCF-B 方法种子。继续堆同源实验的预期信息增益低于停止并保存负面结论。
