# v015 原生研究子智能体草案：非单调验证进度

> 身份与权限：这是 Codex App 原生 Research Subagent 的非权威独立预勘探，只供主研究者裁决。本文没有修改 `hypotheses`、`portfolio`、`Decision` 或 Run 状态，也没有读取其他 Run。检索截止时间为 2026-08-13（Asia/Shanghai）；只把一级论文、论文作者公开工件和正式项目工件用于方法判断。

## 一、结论先行

**当前宽核应明确 KILL。** 问题是真问题：Push Your Agent / PushBench 的 `StateQGP`、`UnitQGP` 把验证通过的不同工作单元暴露为可累计的进度，却没有把“后续写入使早先通过结果失效”建模成一等事件。但是，拟议的计算——记录验证时的读足迹，后续动作给出写足迹，求最小可能失效前沿，撤销缓存的通过状态，按风险/成本选择性重验，并要求终局在同一新鲜快照上成立——没有留下智能体特有的不可约计算。

它可被现有谱系逐项精确重构：

1. `读足迹 + 写变化 + 最小受影响闭包` 是自调整计算的动态依赖图和增量构建系统的脏节点传播；
2. `撤销先前通过 + 只重跑可能受影响验证器` 是安全回归测试选择，尤其与 Ekstazi 的动态文件依赖分析—执行—收集三阶段几乎逐字段同构；
3. `风险/成本调度重验` 是回归测试优先级排序；
4. `同一新鲜快照才允许终止` 是版本检查、乐观并发控制或 Atomix 的读版本失效—中止—重试；
5. `撤销派生进度并重建` 已被 MemTX 的来源依赖图级联失效覆盖；
6. `验证单元发生变化后修复证明` 比本候选更强地改变输出对象，而本候选只选择并重跑验证器。

因此，候选对 Push Your Agent 的确是一个**正确的基准语义修补**，但对方法文献只是：

> `PushBench/UnitQGP 控制器 + Ekstazi/Shake 式动态依赖和缓存失效 + Atomix 式快照版本检查 + 回归测试优先级排序`。

这属于强组件组合，不是新的方法核。若把读/写足迹从确定性审计信息改成由大语言模型推断的“语义足迹”，则 changed computation 转为依赖或动作影响模型学习：它既不再能保证最小且安全的失效前沿，又落回本 Run 已淘汰的语义足迹/动作模型路线。TEBench 的结果进一步说明，仅靠结构依赖追踪识别语义陈旧测试并不完备；这暴露的是足迹不充分，而不是新的失效传播算子。

**本次未发现无法由上述谱系表达的新对象，因此不给 `CONDITIONAL SURVIVE`。** 可以保留“非单调 QGP”作为 PushBench 的测量扩展或负结果实验，不应作为 CCF-B 方法种子晋升。

## 二、候选计算的最强形式化

令环境在动作前的可审计快照为 `s_t`，工作单元集合为 `U`。一次验证通过不是永久布尔值，而是证书：

\[
c_u^t=(u,s_t,R_u^t,\phi_u^t,h_u^t,\texttt{PASS},r_u,k_u),
\]

其中：

- `R_u^t` 是验证器在快照 `s_t` 实际读取的资源/键/文件/对象及版本；
- `\phi_u^t` 是验证条件或验证器版本；
- `h_u^t` 是输入摘要；
- `r_u,k_u` 是失败风险与重验成本。

动作 `a_t` 产生已审计写足迹 `W(a_t)`。在足迹完整、版本可靠的前提下，直接失效集可写为：

\[
I_0(a_t)=\{u:\ R_u^t\cap W(a_t)\neq\varnothing
\ \lor\ \phi_u^t\text{ changed}
\ \lor\ \operatorname{ver}_{s_{t+1}}(R_u^t)\neq\operatorname{ver}_{s_t}(R_u^t)\}.
\]

若工作单元之间还有派生依赖图 `G_U`，则候选求 `I=Reach^+_{G_U}(I_0)`，把 `I` 中证书置为 `DIRTY/UNKNOWN`，再按 `r_u/k_u` 或其他代价函数调度验证。每次重验既更新通过/失败状态，也重新收集动态读足迹。终止条件不再是历史通过数达到 `N`，而是存在同一快照 `s*`，使所有计入完成的单元都拥有针对 `s*` 或其未变化资源版本的有效证书。

相对 Push Your Agent，这确实改变了进度定义：

\[
\texttt{valid\_count}_t
=|\{u:\operatorname{status}_t(u)=\texttt{PASS}
\land \operatorname{fresh}(c_u^t,s_t)\}|,
\]

且该值可下降。问题在于，上述每个新增算子都已有直接对应物。

## 三、Push Your Agent / PushBench：真实缺口，但只是局部新颖

### 3.1 输入—计算—输出

Push Your Agent 把定量目标持久性任务定义为 `(环境 E, 目标 T, 外部验证器 V, 目标数量 N, 交互预算 B)`；工作单元可以是积压项、数据记录、文件块、代码位置、测试用例或构建目标。其进度是不同已提交标识符中 `V(x)=1` 的数量，达到 `N` 即完成。`StateQGP` 记录已提交标识符、已见搜索页和翻页状态；`UnitQGP` 记录单元状态，修复陈旧检查、编辑后未运行验证器、无提交循环，并把策略路由回待处理或已尝试单元。

- **输入**：任务清单、单元、验证器反馈、目标数量和预算。
- **计算**：记录已接受/重复/待处理状态；阻止未达到目标时结束；把策略路由到待处理单元和验证器。
- **输出**：累计的不同验证通过数、剩余数、终止资格和控制器动作修复。

论文的 QGP-SWE-lite 把每个有效单元做成问题式修复或检查，也明确观察到“编辑后未运行验证器”失败；但它仍把成功写成累计的验证通过工作单元，没有定义后续编辑对早先通过证书的撤销、依赖传播或快照一致性。论文给出的匿名工件包括代码、清单、仓库快照和复现脚本，因此它是合适的公开实验载体。

### 3.2 碰撞级别

- 与本候选的**问题碰撞：部分**。PushBench 已有“外部可核验进度状态”，本候选把它从单调计数改成可撤销证书。
- 与本候选的**计算碰撞：无/很弱**。`UnitQGP` 会把策略拉回待验证单元，但不计算写入导致的受影响闭包。
- 与本候选的**输出碰撞：部分**。两者都输出终止资格；本候选增加 `DIRTY/UNKNOWN`、失效前沿和快照新鲜性。

所以，“非单调 QGP”相对该单篇论文有可描述增量；但新颖性必须相对最近方法谱系，而不是只相对起点论文。

一级来源：[Push Your Agent / PushBench（arXiv:2605.23574）](https://arxiv.org/html/2605.23574)，[匿名公开工件](https://anonymous.4open.science/r/artifacts-pushbench-7DB1/README.md)。

## 四、逐谱系 I/C/O 与碰撞审计

### 4.1 自调整计算：方法级精确碰撞

Adaptive Functional Programming 和后续自调整计算把执行表示为动态依赖图：位置到函数调用的读边表示数据依赖，外部内存变化触发变化传播，只重执行受影响调用；关键正确性性质是传播后的内存和依赖图与在新输入上从头执行得到的结果一致。Adapton 进一步用按需计算图，只在观察者需要输出时重算。

- **输入**：旧执行的动态依赖图/计算痕迹、旧内存、外部输入变化、所需输出。
- **计算**：由被改位置沿读/控制依赖传播脏标记；删除或重执行受影响子计算；更新动态依赖图；按需求只物化需要结果。
- **输出**：与新输入上从头执行一致的更新结果和依赖图。
- **对应映射**：验证单元=`函数调用/观察者需要的输出`；验证读足迹=`动态读边`；动作写足迹=`外部内存变化`；撤销通过=`标记旧结果无效`；重验=`变化传播中的重执行`；新鲜终局=`与从头执行一致`。
- **碰撞等级：exact method collision。** 候选没有改变失效检测或传播数学对象，只把计算节点命名为“验证进度单元”。

一级来源：[Adaptive Functional Programming（POPL 2002）](https://www.cs.cmu.edu/~guyb/papers/popl02.pdf)，[Self-Adjusting Computation 博士论文](https://www.cs.cmu.edu/~rwh/students/acar.pdf)，[An Experimental Analysis of Self-Adjusting Computation](https://www.cs.cmu.edu/~blelloch/papers/ABBHT09.pdf)，[Adapton（PLDI 2014）](https://matthewhammer.org/adapton/)。

### 4.2 增量构建与动态依赖：方法级精确碰撞

Build Systems à la Carte 把最小性定义为：每个构建最多执行一次，而且只执行传递依赖于已变化输入的任务。Shake 保存上次构建发现的依赖图和内容哈希，用旧图决定需重建节点；任务运行时还可发现动态依赖，并暂停到依赖变新鲜；输出未变化时可提前截断传播。论文同时指出任务自身变化也应触发重算。

- **输入**：任务定义、目标键、上次动态依赖图/痕迹/哈希、当前键值或文件哈希。
- **计算**：比较资源版本；沿依赖图确定过时键；按依赖序重建；运行时补充动态依赖；结果未变时提前截断。
- **输出**：所有请求目标均新鲜的构建状态及更新后的依赖元数据。
- **对应映射**：验证条件=`构建任务`；通过证书=`缓存产物/痕迹`；动作写入=`输入键变化`；最小失效前沿=`最小需重建键集`；重验=`重建`；同一快照完成=`目标全部 up-to-date`。
- **碰撞等级：exact method collision。** “验证不是构建”只改变任务语义，不改变计算。

尤其致命的是动态依赖和验证器变化都不是逃生点：Shake 会在执行时发现新依赖，Excel 式自跟踪会在公式自身变化时重算，均已在该统一框架内表达。

一级来源：[Build Systems à la Carte（ICFP 2018）](https://simon.peytonjones.org/assets/pdfs/build-systems-original.pdf)，[扩展期刊版及可执行代码入口](https://www.microsoft.com/en-us/research/publication/build-systems-a-la-carte/)。

### 4.3 安全回归测试选择 / 测试影响分析：逐字段精确碰撞

Rothermel–Harrold 的安全回归测试选择从旧/新程序、测试套件和旧测试执行信息中，选择所有行为可能受修改影响的测试；“安全”要求不能漏掉任何可能暴露新程序故障的旧测试。Ekstazi 把这一谱系压到与本候选几乎相同的接口：每个测试实体运行时收集访问文件及校验和；新修订先比较这些文件是否变化，变化则选择该测试执行；执行后重新收集依赖供下一修订使用。它还跟踪访问过但当时不存在的文件，以覆盖“后来创建文件改变行为”的负依赖。

- **输入**：测试实体、旧执行收集的文件读依赖和哈希、当前文件系统/新修订。
- **计算**：分析阶段比较依赖文件哈希并选择受影响测试；执行阶段重跑；收集阶段更新每个测试的动态依赖。
- **输出**：可能受影响的最小/保守测试子集、当前测试结果、下一轮依赖文件。
- **逐字段映射**：
  - `u` ↔ test entity；
  - `R_u` ↔ 测试访问的文件/类/外部资源；
  - `W(a)` ↔ 新修订中哈希变化的文件；
  - `PASS` ↔ 上次测试结果；
  - `I_0` ↔ Ekstazi 分析阶段所选测试；
  - 重验 ↔ 执行阶段；
  - 更新足迹 ↔ 收集阶段。
- **碰撞等级：exact method and interface collision。** 这是当前最强、最窄、最公平基线，不是“相关工作之一”。

粗细粒度权衡同样已知：Ekstazi 故意用文件级依赖换取低收集/分析成本，细粒度方法可能选择更少测试但端到端更慢；候选所谓“最小成本前沿”必须与同足迹粒度的基线比较，不能把更强插桩只给自己。

一级来源：[A Safe, Efficient Regression Test Selection Technique（TOSEM 1997）](https://www.cs.purdue.edu/homes/xyzhang/fall07/Papers/p173-rothermel.pdf)，[Practical Regression Test Selection with Dynamic File Dependencies / Ekstazi（ISSTA 2015）](https://mir.cs.illinois.edu/~marinov/publications/GligoricETAL15PracticalRTS.pdf)。

### 4.4 风险/成本调度：组件精确碰撞

回归测试优先级排序明确把测试重排为优化某个性能目标，例如更快故障暴露，并利用以往测试执行和覆盖信息构造顺序。本候选的 `risk/cost` 排序只是换一个优先级函数；除非提出新的可证明调度目标与算法，否则不能充当 changed computation。

- **输入**：待重跑测试、覆盖/历史/风险/成本特征、性能目标。
- **计算**：求使目标函数更优的测试排列。
- **输出**：重验顺序。
- **碰撞等级：exact component collision。** 

一级来源：[Prioritizing Test Cases for Regression Testing（IEEE TSE 2001）](https://digitalcommons.unl.edu/csearticles/9/)。

### 4.5 证明修复：问题部分碰撞，方法不构成逃生点

PUMPKIN Pi 接收旧证明、类型变化及类型等价配置，把旧证明项变换为只引用新类型的新证明项，再反编译为建议证明脚本。它处理的是“变化使证明破裂后如何产生修复后的证明”，比本候选的“找出可能失效证明并重新检查”更强。

- **输入**：旧类型/新类型之间的等价配置和旧证明项。
- **计算**：跨等价传输证明项；消除旧类型引用；反编译为策略脚本。
- **输出**：新证明项和建议证明脚本。
- **碰撞等级：partial problem / component collision。** 两者都处理变化后的验证资产；但证明修复改变证明内容，本候选只做失效选择与重验。它不能为候选提供新算子，反而说明若只重验，方法贡献更弱。

一级来源：[Proof Repair across Type Equivalences（PLDI 2021）](https://homes.cs.washington.edu/~djg/papers/pldi21pumpkin.pdf)，[PUMPKIN Pi 工件](https://zenodo.org/records/4671079)。

### 4.6 Atomix：同一新鲜快照的精确碰撞

Atomix 的事务记录读作用域和效果作用域，封存足迹后才允许提交。每个资源有版本计数；读取时记录版本，若提交前版本变化，则 `ReadIsStale` 失败，事务中止并在新状态上重试。其每资源进度前沿还要求更早冲突事务已终结。

- **输入**：事务读作用域/效果作用域、读取版本、资源当前版本、纪元和每资源前沿。
- **计算**：比较读版本；版本变化则判陈旧并中止重试；只在相关进度前沿满足时提交。
- **输出**：基于新鲜读取的提交，或陈旧中止及重试。
- **碰撞等级：exact component collision。** 候选的“所有完成条件必须在同一新鲜快照上成立”是把这一提交检查应用到一组验证证书。

Atomix 还明确说明，作用域太粗会安全地降低并发，作用域遗漏或过窄会放过陈旧读取。这与候选读/写足迹的声称边界完全相同。

一级来源：[Atomix: Timely, Transactional Tool Use for Reliable Agentic Workflows（arXiv:2602.14849）](https://arxiv.org/html/2602.14849)，[公开代码](https://github.com/mpi-dsg/atomix)。

### 4.7 MemTX：依赖证书撤销与级联重建的强组件碰撞

MemTX 的每条记忆记录携带来源边形成派生有向无环图。撤销记录时，它遍历所有传递后代：信念被撤销，摘要/画像/索引/共享副本被隔离为失效并等待从仍存活来源重建，工具动作则补偿或记录泄漏；其不变量要求撤销后所有非终结后代都不活跃。

- **输入**：带来源边和类型的记录图、快照事务、被撤销记录。
- **计算**：沿传递来源后代级联失效；按类型撤销、隔离重建、补偿或登记泄漏。
- **输出**：无已撤销祖先的活动记录集、待重建视图和回滚日志。
- **碰撞等级：strong component / near-exact object collision。** 把“记忆派生记录”替换成“已验证工作单元证书”，就是候选的撤销及最小传递前沿。

一级来源：[MemTX: Transactional Belief Commit for Stateful Agent Memory（arXiv:2607.23929）](https://arxiv.org/html/2607.23929)。

### 4.8 Cordon：验证前提交、回滚和边界完整性的组件碰撞

Cordon 把多个模型回合、产物、重试和派生提示包进语义事务，记录结果血缘、可恢复本地写/删和外部效果；提交前验证，失败时恢复本地锚点并阻止暂存外部效果释放。它要求每个有副作用操作在提交前进入事务表示，未被中介的变化只能作为越界事件报告。

- **输入**：事务范围、结果血缘、写删集合、外部效果和验证条件。
- **计算**：在影子状态执行并验证；满足条件则提交，否则回滚/补偿。
- **输出**：已提交或已回滚的状态、效果及审计证据。
- **碰撞等级：component collision。** Cordon 不选择历史验证单元，但已覆盖“终局前所有变化必须被观测且验证；漏足迹不能声称保证”的事务外壳。

一级来源：[Cordon: Semantic Transactions for Tool-Using LLM Agents（arXiv:2606.17573）](https://arxiv.org/html/2606.17573)。

## 五、智能体/编码工作中的“陈旧进度”：窄缺口仍不能救方法核

### 5.1 TEBench：语义陈旧是足迹完备性的反例

TEBench 给定项目仓库和生产代码提交，要求编码智能体识别需要修改的现有测试及需要新增测试的位置，再生成测试补丁。它把演化分成测试破裂、测试陈旧和测试缺失；其中“测试陈旧”指测试在新代码上仍通过，却不再有意义地验证更新语义。七种智能体配置的陈旧测试识别 F1 约为 36%，论文还报告穷尽式结构依赖分析的召回率只有 66%。

- **输入**：项目、生产代码变化、旧测试套件。
- **计算**：跨项目识别破裂/语义陈旧/缺失测试并生成更新。
- **输出**：测试识别集合和测试补丁。
- **碰撞等级：problem/component collision，不是同一方法。** 它证明“运行时读过哪些文件”不等价于“验证条件是否仍能表达新的需求语义”。

这没有产生候选的逃生点。若候选坚持确定性最小前沿，它只能对**已声明、可审计的依赖宇宙**保证安全；若要覆盖 TEBench 式语义陈旧，就必须引入需求—测试语义关系识别、测试演化或新增验证义务，输出不再只是旧证书失效前沿。那是另一个问题核，而且现有 TEBench 已直接占据其问题定义。

一级来源：[TEBench 论文（arXiv:2605.06125）](https://arxiv.org/html/2605.06125)，[公开代码与数据入口](https://github.com/iSEngLab/TEBench)。

### 5.2 验证证据与精确工作树状态：快照戳已有直接先例

Validation Evidence in LLM Repair Agents 对每个自主选择的验证命令记录命令、输出、退出码和执行时的精确工作树状态，把验证产物提取成测试补丁，并在原始缺陷状态、候选状态和开发者正确修复状态上重放，以判定一次“通过”是否真的区分缺陷。

- **输入**：验证事件、事件时精确工作树、测试补丁、三种代码状态。
- **计算**：跨状态确定性重放并分配证据角色。
- **输出**：验证事件的证据充分性类别。
- **碰撞等级：component collision。** 它已占据“通过证据必须绑定产生它的精确状态”；但其目标是证据判别性，不是失效传播。

该工作还暴露候选没解决的另一问题：即使证书新鲜，验证器也可能对目标缺陷无判别力。新鲜性不是充分性；把两者合并会扩张成第二个方法问题。

一级来源：[Validation Evidence in LLM Repair Agents（arXiv:2607.28871）](https://arxiv.org/html/2607.28871)。

### 5.3 Agent-specific 最近邻结论

本次严格检索没有找到一篇把“PushBench 可累计进度”直接改成“可撤销验证证书”的同名智能体论文；这是**表面层的窄空白**。但 nearest-computation 不是空白：

- PushBench 提供控制器和进度对象；
- Ekstazi/Shake 提供完整失效与重验计算；
- Atomix 提供新鲜快照提交条件；
- MemTX 提供派生证书级联撤销；
- TEBench 提供语义足迹不完备的反例与公开任务。

所以这最多支持一篇基准/测量或系统集成论文的问题动机，不支持当前 CRL 所要求的方法种子。

### 5.4 SkillSentry：更近的单调步骤完成状态，但修复仍是经典失效传播

SkillSentry 从技能文档抽取步骤、先决依赖、约束和终止必需步骤，并从轨迹挖掘可观察动作模式。运行时把步骤依赖构成有限状态机；某步骤的所有逻辑动作一旦被匹配，就标为完成并激活后继步骤；终止检查只确认所有必需步骤已被标为完成。论文没有定义后续动作撤销已完成步骤，也没有把完成事实绑定到其读取资源、约束版本或验证快照。因此，若后续工具动作覆盖了早先步骤的产物或前置条件，有限状态机仍可能保留陈旧完成状态。

- **输入**：技能步骤和 `depends_on` 图、逻辑动作模式、实时工具动作轨迹。
- **计算**：匹配动作模式，累计每步已匹配逻辑动作；全部匹配后永久标记步骤完成；依赖满足后激活后继；必需步骤全完成则允许终止。
- **输出**：有限状态机完成/激活状态、过程干预和终止资格。
- **碰撞等级：exact problem witness / partial method collision。** 它是比 PushBench 更直接的智能体层陈旧进度见证，但没有提供写集驱动的撤销计算。给它增加“完成证书读足迹、后续写足迹、传递失效、重验”后，新增部分仍逐项等于动态依赖图、自调整计算、构建系统和回归测试选择；SkillSentry 只提供承载控制器，不产生不可约新算子。

一级来源：[SkillSentry（arXiv:2608.09253）](https://arxiv.org/html/2608.09253)。

## 六、为什么“智能体语义”不是不可约 changed computation

候选只有两种可实现解释，两者都致命：

### 6.1 足迹由工具/验证器真实插桩或契约给出

此时失效前沿可确定性、安全地计算，但计算与 Ekstazi/Shake/自调整计算精确等价。验证单元可以是文本约束、代码测试、数据库一致性检查或工具任务；只要它被表示为“读取一组有版本资源并输出结果的任务”，构建系统抽象就能表达。资源键不必是文件，可以是文档段落、数据库行、API 对象、策略版本或外部实体版本。

### 6.2 足迹由大语言模型从自然语言和历史轨迹推断

此时“最小可能失效前沿”不再可证明：

- 漏依赖造成假新鲜和错误终止；
- 过宽依赖退化为每次全量重验；
- 新出现资源、缺失/存在性谓词和跨命名空间别名都需要额外语义解析；
- 验证器本身若随机或环境不可重放，单一新鲜快照也不能产生确定性证书。

这把研究贡献移到“如何学习保守且校准的语义依赖/写影响模型”，而失效传播仍是经典算子。并且本 Run 既有负结果已经禁止把从工具模式或轨迹推断的语义足迹再次包装为新对象。即便忽略该 Run 内约束，TEBench 的结构依赖召回缺口也说明仅靠直接足迹不能支持全称安全声明。

### 6.3 负依赖、动态依赖和验证器写入都不是新对象

- “某文件/对象不存在”是负依赖；Ekstazi 已跟踪曾尝试访问但不存在的文件。
- 依赖由值决定是动态依赖；Shake 和自调整计算会在重执行时更新依赖图。
- 验证器自身改动是任务定义变化；自跟踪构建会重算。
- 验证器产生写入或外部效果是事务/效果隔离问题；Atomix 与 Cordon 已提供作用域、暂存、回滚和补偿。

因此目前没有剩余的、只能由“智能体非单调进度”表达而不能由上述谱系表达的科学对象。

## 七、最小高信息量 killer experiment

### 7.1 可公开运行载体

首选 PushBench 匿名工件中的 QGP-DataOps-lite / QGP-SWE-lite，而不是另造完全合成基准。论文工件已含控制器、工作单元、确定性检查器、仓库快照与复现脚本。给每个工作单元增加：

- 验证时资源版本和实际文件读取集合；
- 后续编辑的文件写集合；
- 一个 `PASS / DIRTY / FAIL` 状态；
- 隐藏的最终全量检查器。

构造 24 个很小的“先通过—后失效”积压任务，每个只含 6–10 个单元，覆盖三类确定性结构：直接共享文件、传递依赖、负依赖（先前不存在的文件后来创建）。通过前置条件强制代理先完成单元 `u1`，再完成必须改写共享资源的 `u2`，使 `u1` 的旧通过结果失效。这样无需昂贵的大模型规模实验就能暴露单调计数错误。

如果 PushBench 匿名工件临时不可取得，次选公开 TEBench 的 314 个 Java 演化任务用于验证足迹完备性；但 TEBench 的终局是测试演化补丁，不能作为当前方法新颖性的主载体。`tau-bench` 更适合事务并发与外部状态，不如 PushBench 直接隔离“进度撤销”。

### 7.2 四个同信息条件

1. **UnitQGP-monotone**：原始累计通过状态，不撤销；
2. **Retest-all**：每次写入后重跑全部已通过单元；
3. **Ekstazi/Shake baseline**：同一读足迹、文件哈希和工作单元依赖图，选择受影响单元并重跑；
4. **Proposed**：候选的最小前沿、撤销、风险/成本调度与快照证书。

关键公平约束是 3 与 4 获得完全相同的插桩、读/写足迹、版本信息、风险和成本。不能把“智能体控制器”当方法增量，却不给经典基线同一状态。

### 7.3 独立终局与指标

冻结最终工作树后，由不向控制器暴露的独立脚本全量运行所有单元检查器和跨单元一致性检查器。主要指标：

- 错误完成率；
- 失效召回率与精度；
- 从写入到撤销之间的陈旧通过面积；
- 重验次数/时间；
- 最终真实完成率；
- 所选失效集与 Ekstazi/Shake 基线的逐轨迹集合相等率。

### 7.4 预注册 kill 条件

满足任一项即杀，当前文献推断强烈预期第 1 项成立：

1. 在相同足迹上，Proposed 与 Ekstazi/Shake 对所有确定性轨迹输出完全相同的失效集合和终止资格；调度只造成已知优先级差异；
2. Proposed 的任何收益在给经典基线相同插桩、版本和风险/成本特征后消失；
3. 在语义陈旧或漏足迹任务上出现任何假新鲜，却仍声称确定性安全/最小性；
4. 为避免假新鲜而退化成每次全量重验，成本不优于 Retest-all；
5. 方法差异只剩状态字段名、提示文本、控制器路由或 PushBench 的工程接线。

这个实验的杀伤力高于直接做大规模智能体对比：它先检验 changed computation 是否与最近强基线逐轨迹同构。如果同构，模型规模和端到端成功率都不能挽救方法新颖性。

## 八、最终裁决与可保留负知识

### 8.1 裁决

**KILL：当前“非单调验证进度”宽核不应晋升。**

理由不是问题不重要，而是：

- 相对 PushBench 的改动是真实而清楚的；
- 相对增量计算、构建系统和回归测试选择的 changed computation 为零；
- 快照、级联撤销和调度又分别被 Atomix、MemTX 和测试优先级排序吸收；
- 一旦诉诸语义足迹，确定性安全声明失效，贡献转移到另一个已知且本 Run 已有负结果的依赖学习问题。

### 8.2 建议记录的负结果

可记录为可复用禁止项：

> 不得把“验证结果绑定读版本，写入后沿依赖图撤销并选择性重验”作为智能体特有方法核重新进入；在显式足迹下它等于增量构建/安全回归测试选择，在推断足迹下它等于不完备的语义依赖/动作影响学习。`同一快照`、`级联撤销`、`风险/成本调度`分别是事务版本检查、来源图修复和测试优先级组件，不能累加出新方法贡献。

### 8.3 可留下但不晋升的资产

- `valid_count` 应允许下降的 PushBench 指标修订；
- “陈旧通过面积”“错误完成率”“同快照全量终局”三个测量量；
- 上述 24 个先通过—后失效的最小积压任务；
- 对任何未来候选的最强基线要求：同足迹的 Ekstazi/Shake + Retest-all + 版本检查。

这些资产有基准/诊断价值，但不能被误报为已存活的研究 Seed。
