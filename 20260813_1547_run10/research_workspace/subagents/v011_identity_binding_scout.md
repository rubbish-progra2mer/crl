## 一句话结论

**按当前表述应杀（KILL-AS-STATED）。** 2026 年 6 月的 *Entity Binding Failures in Tool-Augmented Agents* 已经直接提出“正确工具、错误实体”、实体解析前置条件、候选比较、置信门控、歧义澄清和实体溯源，并公开了 60 任务诊断基准；PACT 又已经提出参数语义角色、跨步骤值溯源、未解除义务和作用域受限证书；IGAC 已经提出服务器签发的短期意图证书、资源 / 效果边界、工具—载荷一致性检查和状态见证。把这些部件组合后再命名为“实体绑定证书”，无法形成可辩护的方法新颖性。

仍有一个**很窄、必须用实验决定是否保留**的重构空间：不要再主张“证书 / 溯源 / 动作门控”，只主张一个此前工作未明确给出的内部判定——**跨命名空间身份等价的来源折叠、不可循环连接证明**。它必须识别“多个表面证据实际复制自同一上游”与“目标候选用自身字段循环证明自身”的情况，并在不访问隐藏真值的前提下，为目标写操作生成可复查的连接见证。如果这个判定不能在匹配预算下击败 `Entity-CMTF + 经典实体解析 + PACT-L3 + IGAC 资源边界` 的组合强基线，则整个方法家族应杀。

## 1. 直接失败证据与最邻近工作

### 1.1 直接同题碰撞：Entity Binding Failures in Tool-Augmented Agents（2026）

主来源：

- 论文：[arXiv:2606.30531](https://arxiv.org/abs/2606.30531)
- HTML 全文：[方法与实验](https://arxiv.org/html/2606.30531)
- 公开代码与数据：[R-Suresh/EntityBindingFailures](https://github.com/R-Suresh/EntityBindingFailures)

可核对事实：

- 论文把“工具选对但目标实体选错”单独形式化为 entity binding failure（实体绑定失败）。
- 方法在工具执行前插入实体感知动作门：为每个工具声明实体解析前置条件，检索候选实体，比较候选，记录实体标识、邮箱、所有者、时间、线程、账号等溯源证据；解析不足时澄清或弃权。
- 基准覆盖邮件、日历、文档、客户记录、问题跟踪五域，含名字冲突、版本、时间、账号冲突、近重复、跨系统和真实歧义。
- 60 个任务、5 个模型、6 种方法、1,800 次运行中，动作优先方法在工具错误率为 0 的同时仍有 24%–26% 错误实体操作；置信门控和 `Entity CMTF + provenance` 把错误实体操作降为 0。
- 但安全是以显著弃权换来的：仓库汇总中，`confidence_gate` 的任务完成率 / 安全成功率为 31.7% / 40.0%，`entity_cmtf_provenance` 为 26.0% / 34.3%，而动作优先方法任务完成约 74%–75%。
- 作者明确说明诊断实现使用结构化提示和候选比较，不是经过校准的生产级不确定性模型。这留下“如何恢复可解析任务效用”的空间，但没有留下“实体感知门控 + 溯源 + 澄清”这一主张空间。

碰撞判断：

- 问题层：**exact（完全碰撞）**。
- 外层方法流：**exact（完全碰撞）**，即“解析实体 → 记录溯源 → 提交前门控 → 澄清 / 弃权”。
- “携带证明到后续步骤”：论文只要求记录溯源，没有给出严格的跨步骤证明代数，因此这一点是 partial；但仅把记录改名为 certificate 不构成 changed computation（计算变化）。
- 评价层：公开诊断任务可直接作为近邻基线，但它不是状态真实变更的独立终局，不能单独承担最终方法证据。

### 1.2 参数级跨步溯源与证书碰撞：PACT（2026）

主来源：[The Granularity Mismatch in Agent Security: Argument-Level Provenance Solves Enforcement and Isolates the LLM Reasoning Bottleneck](https://arxiv.org/html/2605.11039)

可核对事实：

- PACT（溯源感知能力契约）给工具参数分配 `target / command / credential / content / selector / control` 六类语义角色。
- 每个运行时值携带来源集合、信任级别和未解除义务；值组合时保守合并来源、取最低信任并合并义务；跨重规划步骤持续传播。
- 工具执行前逐参数检查角色需要的信任、禁止来源和义务。
- L3 “认证路由”使用作用域受限的解除证书；证书保留原始来源，只能解除指定谓词，不能跨角色复用。
- PACT 在 AgentDojo 上把“目标参数被非可信内容劫持”视为 authority binding（权限目标绑定），而非一般内容污染；消融称语义角色和跨步溯源都必要。
- 论文报告自动合成阶段在 20 个真实 MCP 工具上角色准确率 87.1%、溯源准确率 77.4%，说明真正瓶颈是上游溯源推断与契约合成，而不是证书检查本身。

碰撞判断：

- “类型化目标参数”：**exact component（完全组件碰撞）**。
- “从读取结果跨步骤携带溯源到写操作”：**exact component**。
- “提交前检查未解除义务 / 作用域证书”：**exact component**。
- PACT 的威胁模型主要是间接提示注入与非可信来源绑定权限参数，不保证两个可信记录是否属于同一现实实体；所以“身份等价证明”的内部语义仍可能是 partial 差异。

### 1.3 意图证书、资源边界与状态见证碰撞：IGAC / OpenPort（2026）

主来源：[Intent-Governed Tool Authorization for AI Agents](https://arxiv.org/html/2606.22916)

可核对事实：

- IGAC 把经认证用户请求转成服务器签发、短期有效的意图证书，绑定用户、应用、租户 / 工作区、会话、消息、规范化版本、静态策略版本和工具注册表版本。
- 证书含动作类别、资源边界、效果边界、置信度和最大路由结果；规划前缩小工具清单，规划后检查工具—载荷—效果一致性。
- OpenPort 底层已有草稿优先写入、预检影响哈希、可选状态见证、幂等与审计。
- IGAC 对“删除某个具体记录”明确把资源标识绑定进证书，若目标从 `rec-123` 变成 `rec-124` 则拒绝。
- 论文自己的限制很强：真实模型运行中未完成不安全效果，但仍接受 40/198 个意图不一致草稿路径；严格良性完成为 0/108，仅 36/108 产生受治理产物。作者把证书精度称为主要瓶颈。

碰撞判断：

- “证书绑定请求与目标资源”：**exact component**。
- “提交前一致性 / 状态见证 / 失败关闭”：**exact component**。
- IGAC 不负责从名字、邮箱、电话和应用局部标识推导现实实体等价，因此身份连接算法本身只发生 partial 碰撞。
- 若候选只是在 IGAC 的 `resourceBounds` 中加入 `email / phone / external_id` 字段，则应直接杀：这是策略字段扩充，不是新计算。

### 1.4 经典实体解析与带溯源的实体解析

主来源：

- 综述：[(Almost) All of Entity Resolution](https://arxiv.org/abs/2008.04443)
- 带溯源修复：[Provenance-Aware Entity Resolution](https://users.cecs.anu.edu.au/~u5170295/papers/dasfaa-wang-2015.pdf)
- 跨数据库图实体与字段溯源：[Linking Graph Entities with Multiplicity and Provenance](https://arxiv.org/abs/1908.04464)

可核对事实：

- 实体解析 / 记录链接长期处理名字、邮箱、电话等多字段不一致，把不同数据库记录链接到同一潜在实体；确定性、多字段概率、图匹配、聚类、传递性和不确定性量化均已有成熟谱系。
- 2015 年工作已经记录实体解析过程的溯源并用其定位、修复错误匹配。
- Certus 使用带来源、有效期和安全属性的图式实体资料跨数据库及文本提及做链接。

碰撞判断：

- “跨命名空间连接名字 / 邮箱 / 电话 / 外部标识”：**partial-to-exact（部分到完全）**，取决于候选是否只是普通记录链接。
- “给连接边保存来源和有效期”：**exact component**。
- “实体解析结果驱动智能体提交或澄清”：传统工作没有动作循环与副作用，因此仍是 partial。
- 若“非循环见证”最后只是“至少两个字段匹配”“多个来源投票”或实体图上存在路径，则应杀：分别被确定性实体解析、概率记录链接和图实体解析吸收。

### 1.5 真实 AppWorld 失败信号与强提示基线

主来源：[Agentic Context Engineering（ACE）](https://arxiv.org/abs/2510.04618)；其 ICLR 2026 论文附录中的 AppWorld 诊断示例可在[正式 OpenReview 版本](https://openreview.net/pdf?id=eC4ygDs02R)核对。

直接失败示例：智能体试图从 Venmo 交易描述中的关键词识别“室友”，而没有用 Phone 应用联系人关系作为权威来源，导致错误地只算出 79.0 而非 1068.0。这个例子证明：跨应用身份选择会被“看似相关但不是身份权威”的来源误导，且终局错误由 AppWorld 单元测试给出，不是由候选方法自评。

同时，ACE 的可复用经验会生成类似“身份关系必须从 Phone 联系人而不是交易描述解析”的详细操作手册。因此，一个固定的“优先权威来源”提示 / 操作手册是必须比较的强基线；若它与证书法相同有效，则证书没有方法价值。

## 3. 可救变体的最窄 changed computation

候选若继续，建议放弃泛化名称“携带溯源的实体绑定证书”，只保留下面的计算：

1. 把读取到的记录值表示为 `v = (namespace, entity_type, local_id, field, value, source_event, upstream_roots, validity)`。
2. 对用户提及 `m` 和目标应用候选 `e_t` 构造身份连接图。边不是“模型说相似”，而是可重放的外部查找或字段等式，例如：
   `Phone.contact#17 --email==alice@x--> Venmo.user#932`。
3. 用来源依赖关系把复制自同一上游的字段折叠为一个根。两条分别来自“邮件正文”和“由该邮件生成的 CRM 备注”的证据不能算两份独立证据。
4. 禁止循环自证：若候选 `e_t` 的字段先被模型选中，再被写入 / 回显到另一个查询并返回，返回值不能反过来证明最初选择；仅有目标应用自己的显示名也不能证明跨应用同一性。
5. 只在存在满足类型、时效和来源独立性契约的连接见证时，把 `e_t.local_id` 释放给具有副作用的目标参数；否则澄清 / 弃权。
6. 证书只是这一判定的可审计序列化，不是贡献本体。

最小形式可以写成：

```text
Bind(m, e_t) = true
iff exists path p: m -> e_t
     TypeValid(p)
  && Fresh(p)
  && RootCollapsed(p)
  && NonCircular(p, e_t)
  && SourcePolicy(p)
```

关键科学区别必须是 `RootCollapsed + NonCircular` 改变了允许 / 澄清决策；如果去掉它们结果不变，或它们可由固定“查 Phone 再查 Venmo”规则替代，则没有方法核。

## 4. 最强公平基线

最低限度需要以下基线；不能只和 ReAct 或“直接执行”比较：

1. **Entity-CMTF + provenance**：直接复用 2026 同题论文的实体解析前置条件、候选比较、溯源与澄清。
2. **经典实体解析动作门**：确定性多字段 / Fellegi–Sunter 式记录链接 + 阈值 + 澄清；相同候选、相同字段、相同调用预算。
3. **ACE 权威来源操作手册**：明确告诉模型“关系从 Phone 等权威应用解析，不从交易描述推断”，检验结构机制是否只是提示知识。
4. **PACT-L3**：把收件人、账号、外部标识设为 `target / selector`，传播跨步来源，提交前要求目标角色义务解除。
5. **IGAC 资源边界**：请求证书绑定允许的实体 / 目标集合；不一致则澄清或拒绝。
6. **组合强基线**：`Entity-CMTF + 经典实体解析 + PACT-L3 + IGAC resourceBounds`。候选真正新增的只能是来源折叠与非循环证明。
7. **Oracle identity map（仅上界）**：使用隐藏的规范人物映射，不作为公平基线，只量化解析之外的剩余错误。

## 5. 公开可运行基准与“独立终局”可行性

### 5.1 EntityBindingFailures：最接近但只适合诊断 / 近邻复现

- 仓库公开 60 个任务、生成器、运行器、评分与保存结果；本地可重建任务和汇总保存结果，完整复跑原模型需要 AWS Bedrock 权限。
- 这是最直接的最近工作复现和 prompt-level 基线。
- 局限：诊断环境把环境状态与候选作为模型输入，输出是结构化动作 / 澄清；没有真实多应用数据库写入与由最终状态判定的副作用。因此不能单独作为正式独立终局。

### 5.2 AppWorld：可提供独立最终状态，但原生身份扰动不足

主来源：[StonyBrookNLP/appworld](https://github.com/StonyBrookNLP/appworld)，论文：[arXiv:2407.18901](https://arxiv.org/abs/2407.18901)。

- 公开引擎含 9 个日常应用、457 个应用程序接口、约 100 个虚拟用户，任务评价比较初始 / 最终数据库状态并检查意外变化（collateral damage，附带损害）。训练 / 开发任务公开 setup、solution、evaluation；测试集公开 evaluation，可以在本地运行评估。
- 这是当前最合适的**独立终局**：评价器只看隐藏规范人物映射和最终数据库变化，不读取候选证书。
- 但 AppWorld 的 `MainUser` 生成器会为各应用账户同步姓名、邮箱和电话。原生世界因此弱化了“命名空间不一致”与身份漂移；若直接跑原任务，很可能只测普通长程规划。
- 必须在训练 / 开发世界上新增**身份压力扰动**：各应用局部标识不同，别名 / 旧邮箱 / 共享电话 / 同名者受控出现，同时把规范人物映射只留给 evaluator。不要把规范映射暴露给方法。

### 5.3 AppWorld-UL：澄清 / 弃权评价的直接工具

主来源：[AppWorld-UL 论文与代码入口](https://arxiv.org/html/2607.20536)。

- 2026 年 7 月公开 516 个用户在环任务，系统性引入欠指定、不可行和需要批准三类扰动；用受知识边界约束的模拟用户回答澄清问题。
- 它已经覆盖“多个可行目标时应澄清”，且评价最终状态与交互质量。
- 可复用其 perturbation（扰动）框架，把移除的信息改成跨应用身份连接信息；但仍需新增来源相关性 / 循环证据条件。

### 5.4 tau-bench / tau3-bench：身份校验基线，不是跨应用终局

主来源：[tau-bench retail policy](https://github.com/sierra-research/tau-bench/blob/main/tau_bench/envs/retail/wiki.md)，最新代码：[tau2-bench / tau3-bench 仓库](https://github.com/sierra-research/tau2-bench)。

- 零售域政策已要求会话开头通过邮箱或“姓名 + 邮编”定位用户标识，并且即使用户直接提供用户标识也必须校验；高风险数据库更新前必须确认。
- 这是一条很强的固定身份校验基线，并有公开状态模拟和动作评价。
- 但它主要在单一客服域内认证当前用户，不测 Phone → Venmo → Gmail 等跨应用同一人连接，不能独自验证候选核心。

## 6. 最小高信息量杀手实验

### 6.1 环境

在 AppWorld 训练 / 开发任务上建立 24–40 个成对身份压力任务，冻结任务生成器后再运行模型。每个任务由 evaluator 私有的 `MainUser` 映射定义唯一正确目标或 `NEEDS_CLARIFICATION`，方法只能通过正常应用程序接口读取公开字段。

优先任务链：

- Phone 联系人关系 → Venmo 本地用户标识 → 请求 / 支付。
- Phone 联系人 → Gmail 收件地址 → 发送带附件邮件。
- Gmail 发件人 / 线程 → Phone 联系人关系 → Splitwise / Venmo 目标写入。
- 多个室友 / 同事集合 → 多个目标写入，任一错人均算错误实体副作用。

### 6.2 正交条件

每个基础任务至少配以下变体，并保持目标动作和接口相同：

1. **唯一独立见证**：Phone 的权威关系 + 目标应用唯一邮箱 / 电话可以连接。
2. **同名冲突**：两个 Alex，只有独立邮箱或电话能区分。
3. **回声 / 循环自证**：错误候选的显示名出现在交易描述、邮件正文和由其派生的备注中，但这些字段共享同一上游；只有正确 Phone 记录独立。
4. **字段冲突**：姓名指向 A，旧邮箱或共享电话指向 B，要求按预先声明的来源 / 时效策略处理。
5. **真实歧义**：没有非循环连接见证，正确行为是澄清。
6. **可解析但高相似**：多个候选表面几乎相同，固定“总是澄清”会损失效用。

### 6.3 公平性

- 所有方法获得相同工具、候选字段、调用次数 / 令牌预算和澄清机会。
- 证书方法不能读取 evaluator 私有规范标识，也不能获得额外的身份查找接口。
- 固定强基线可以执行与候选相同的 Phone / Gmail / Venmo 查询。
- 最终标签只由初始 / 最终数据库差分与私有规范映射生成；不能用候选证书是否“看起来合理”当正确性标签。

### 6.4 指标

- 错误实体写入率（核心安全指标）。
- 可解析任务完成率。
- 安全成功率：正确完成或在真实歧义中正确澄清。
- 过度澄清率。
- 附带损害数量 / 风险加权错误实体暴露。
- 工具调用数、令牌、延迟。
- 来源折叠 / 非循环检查的消融差异。

### 6.5 杀死条件

满足任一项即杀当前家族：

1. `Entity-CMTF + ER + PACT-L3 + IGAC` 组合强基线在循环 / 相关来源条件下与候选同样安全、同样完成，说明没有新增计算。
2. 候选的收益可由一条固定操作手册“身份关系只查 Phone；用邮箱 / 电话连接目标应用”复现。
3. 所谓非循环见证退化为“两字段一致”“两工具返回相同字符串”“图上存在任意路径”或一般实体解析分数。
4. 错误实体率下降完全来自更多弃权，而安全成功率和可解析任务完成率不优于 Entity-CMTF / PACT。
5. 证书由同一大语言模型既生成又验证，或证明边的来源依赖关系也是模型无外部依据猜出的；这不是外部可复查见证。
6. evaluator 用证书自身规则决定终局，或候选能访问规范人物映射；评价循环 / 真值泄漏。
7. 在原生 AppWorld 同步身份数据上取得收益，但加入别名漂移、共享标识和共同上游后消失；原实验测错了问题。
8. 来源折叠和非循环消融不改变允许 / 澄清决策，证明核心算子是装饰性的。

### 6.6 仅在何种结果下可保留

只有同时出现以下证据，才值得把窄变体升级为候选：

- 组合强基线在“相关证据 / 循环回声”上仍会错误放行；
- 来源折叠 + 非循环连接证明显著减少这些错误；
- 在“唯一独立见证”任务上仍能执行，不是统一弃权；
- AppWorld 独立最终状态确认正确目标且无附带变化；
- 计算差异可写成明确的证明图约束，而不是提示模板或手工应用优先级。

## 7. 总体裁断建议（供主研究者采纳或否决）

- **原始家族：杀。** 问题、门控、溯源、证书、参数类型和提交前检查已分别被直接同题论文、PACT 和 IGAC 覆盖，组合后几乎没有剩余。
- **最窄重构：条件保留到一个杀手实验。** 暂称“来源折叠的非循环身份连接证明”，避免继续声称证书本身新颖。
- **最大风险：** 它很可能只是把经典实体解析、数据溯源和参数级信息流控制堆叠到一起；若没有专门反例证明共同上游折叠改变智能体决策，应立即杀而不是继续做系统工程。
- **最佳评价路径：** EntityBindingFailures 做最近方法复现与提示级先验；AppWorld / AppWorld-UL 身份压力扰动做状态真实变更和独立最终状态；tau3 只作固定身份校验基线。固定 Reviewer 目前不适合调用，因为 changed computation 尚未通过杀手实验。
